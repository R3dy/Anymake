# Project Type: Agentic Harness (`agentic-harness`)

## Identity
- **id:** `agentic-harness`
- **One-liner:** A multi-stage system where LLM agents run in isolated sandboxes, one per pipeline stage, each producing a schema-validated artifact that becomes the next stage's input — coordinated by an orchestration engine and observable through a control/tracing dashboard.
- **Choose this when:** The deliverable *is* the pipeline/engine — any workflow expressible as an ordered (or branching) sequence of agent-driven stages over a backlog of work items, where each stage should run in an isolated, revocable execution environment and hand off a typed, inspectable artifact to the next stage. Examples: a research harness (Search → Synthesize → Fact-check → Draft → Edit), a code-migration harness (Scan → Plan → Transform → Verify → PR), a support-triage harness (Classify → Investigate → Resolve → Escalate), a security-testing harness (Recon → Attack → Grade → Report) — the domain is irrelevant; the shape (staged agents, sandboxed execution, canonical handoffs, centralized backend, tracing, a control surface) is what this type is for.
- **Not this if:** It's one agent answering one request with no multi-stage handoff (`api-service` fronting a single LLM call, or a `saas`/`internal-tool` with an AI feature bolted on) — or the "stages" are just in-process function calls with no need for isolation, a canonical artifact, or independent observability (that's a `library` or a thin `cli`).

## Phase Map
| Phase | Status | Notes |
|-------|--------|-------|
| 0 Foundation | active (full) | Identity, the unit of work ("work item"), the named stage list and its shape (linear / branching / loop-back), success = correctness + reliability + bounded cost per item, not revenue by default |
| 1 Discovery | active (lite/full) | Full if this will be sold/hosted for others; lite if internal/operational. Prior-art pass on existing harnesses/agent frameworks; risk pass on autonomy failure modes (infinite loops, runaway cost, silent drift, tool misuse) |
| 2 Planning | active (full) | "PRD" = **Pipeline & Agent Design** (stage graph + one AgentSpec per stage); UX+Prototype scoped to the control/observability dashboard only; full architecture; monetization optional |
| 3 Solutioning | active (full) | Backlog organized by infrastructure layer (contracts → backend → engine → sandbox → per-stage agents → tracing → control plane → dashboard), not by user-facing feature |

## Success Model
**Reliable, observable, cost-bounded throughput is first-class.** Success = work items move correctly through every stage, autonomy is trustworthy (no silent drift, no unbounded loops, no unbounded spend), every agent action is traceable end to end, and cost per item is known and capped. Revenue is second-class and only applies if the harness (or a hosted version of its dashboard) is itself being sold — most builds of this type are internal operational systems, not products with paying end users.

## Default Stack
Orchestration engine in Python (asyncio or a thread/process pool) or TypeScript/Node, driven by a **declarative stage-graph** (YAML/JSON read at startup — never a hand-coded per-stage dispatch function). Sandboxing via Docker, one ephemeral `docker run --rm` container per stage-run as the reference pattern (a pooled/leased sandbox is an optional latency optimization, not the default). Canonical I/O via typed schemas (Pydantic/Zod) exported to JSON Schema, used both to constrain LLM structured output and to validate every stage handoff. A pluggable backend behind two small interfaces — a **Queue** (publish/claim/release/annotate, with atomic claim for multi-worker safety) and a **Storage** (write/read/list/delete) — with a filesystem/SQLite implementation for local dev and CI, and a production implementation swapped in by config (Postgres, or an existing system of record — ServiceNow, Jira, Linear, a plain database — whatever the team already runs on). Tracing via OpenTelemetry as the interface, shipped to any OTel-compatible collector (Phoenix, Langfuse, Honeycomb, Jaeger, or none) — never call a specific tracing SDK directly from stage/agent code. A small shared **control document or API** (run mode: continuous / step / paused; concurrency; per-stage model overrides) that the engine reads every dispatch cycle. A dashboard (any web framework) that reads the backend + trace store and writes the control document, ideally via SSE/WebSocket for live agent messages rather than polling alone.

## ADRs
- **Mandatory:** ADR-001 Stage-graph definition format (must be declarative/data-driven — adding, reordering, or branching a stage is a config change, never an engine-code change). ADR-002 Sandbox/isolation mechanism (ephemeral-per-run vs. pooled; what's mounted vs. proxied; credential handling — real secrets are never mounted into a stage sandbox). ADR-003 Canonical I/O schema format & versioning (how a stage's output is validated; how the schema evolves without breaking in-flight work items). ADR-004 Backend abstraction (Queue + Storage interfaces; dev/filesystem implementation; production implementation; atomic claim/lease semantics). ADR-005 Tracing/observability backend (OTel interface, chosen collector, span granularity — agent-run / turn / tool-call / token-usage — and trace propagation across the host↔sandbox boundary). ADR-006 Orchestration & concurrency model (worker pool size, single- vs. multi-host fan-out, atomic claim to prevent double-processing, retry/backoff per failure class). ADR-007 Control plane & autonomy modes (how pause/resume/step/concurrency changes reach a running engine; what "one step per agent" means operationally). ADR-008 LLM provider/model routing (model choice per stage, override without redeploy).
- **Optional:** Cost/budget guardrails (max spend per item, circuit breaker); human-in-the-loop approval gate per stage (vs. escalate-on-failure only); multi-tenancy (multiple pipelines/teams on one engine); single-stage replay for debugging; a skill/tool marketplace so new stage capabilities don't require new sandbox images.

## Phase 2 Tracks
- **PRD:** yes — replaced by **Pipeline & Agent Design**: the named stage list (purpose, input state(s), output state(s)/transitions, any loop-back or branch conditions) and, per stage, an **AgentSpec** — system prompt outline, user-prompt template plus which prior-stage output fields populate it, the tool/skill/MCP allowlist, model, and permission mode.
- **UX + Prototype:** yes, but scoped — only the control/observability **dashboard** gets the design system + prototype gate (queue/board view, per-item trace view, run controls). The pipeline itself is headless; there is no end-user-facing UI to prototype beyond that.
- **Architecture:** yes (full) — the 8 mandatory ADRs above.
- **Monetization:** optional — only if the harness (or a hosted dashboard) is itself a sellable product.

## Phase 4 Build Order
`Canonical I/O contracts (typed schemas, JSON-Schema export) → Backend adapters (Queue + Storage: filesystem/dev implementation first, production implementation second) → Stage-graph engine (declarative graph loader + status-transition dispatcher, worker pool, atomic claim) → Agent runner/sandbox (spawn mechanism, mount/proxy policy, exit-code contract) → Per-stage AgentSpecs (prompts + tool allowlists, one stage at a time — implement the simplest/cheapest stage first to prove the loop end-to-end before building the rest) → Tracing integration (OTel spans + cross-sandbox trace propagation) → Control plane (pause/resume/step/concurrency) → Dashboard (read layer over backend + trace store, writes to the control document) → Integration tests (one synthetic work item through every stage) → Deploy`.

Build the contract before the engine, and the engine before any real agent — the first stage you implement should be provably wired into a working end-to-end loop, not debugged as a monolith. The stage-graph loader must exist and be data-driven **before** the first per-stage AgentSpec is written; wiring a new stage should never require editing the dispatcher.

## Experience Harness
**Interaction mode:** Mixed — Request/Run for the pipeline, Browser for the dashboard.
For engine/backend/agent-runner stories: the Experience Runner submits a real
synthetic work item (via `Request` to the queue API or `Run` against a CLI
trigger, per `docs/environment.md`) and inspects the resulting trace/artifact
output at each stage transition against the scripted expectation — this is the
"type a command, get a specific result" case applied to a work item moving
through the graph. For dashboard stories (queue/board view, per-item trace
view, run controls): Browser, same as `saas`, scoped to just those screens.
A story's §3a states which mode(s) its scenarios use.

## Launch & Metrics
Deploy as a long-running service (docker-compose or a container orchestrator), not published to a package registry — unless the dashboard is separately sold as SaaS, in which case apply `saas`'s deploy target to the dashboard only. Metrics: throughput (items/hour per stage), per-stage success/failure/escalation rate, cost per item (LLM token spend), P50/P95 stage latency, queue depth and backlog age, human-escalation rate and resolution time, and trace coverage (% of runs with a complete, unbroken trace). Revenue metrics apply only if monetized.

## Gate Criteria Deltas
- **Skip:** the GUI-prototype gate for the pipeline itself (it's headless); monetization checks unless charging; AARRR/growth-loop metrics; public-launch legal/marketing.
- **Replace:** the prototype gate → a **Pipeline dry-run review** — run one synthetic work item end-to-end through every stage in the dev/filesystem backend, and inspect the full trace plus every intermediate artifact. The dashboard's own prototype (queue/board view, per-item trace view, run controls) is still held to the usual visual-quality bar from `anymake-design-system`, scoped to just those screens.
- **Add:** (1) the stage graph is declarative/data-driven — fail the gate if any stage transition is hard-coded in engine logic rather than the graph config; (2) every stage has a schema-validated output contract with a round-trip validation test; (3) a credential-isolation check — no real secret or API key is ever mounted into or baked into a stage sandbox image, only reachable through a proxied/scoped credential; (4) atomic claim/lease is verified under concurrent workers (no work item is ever double-processed); (5) a complete trace exists for at least one end-to-end run and spans the host↔sandbox boundary (context propagation verified, not just per-process spans); (6) a cost cap or circuit breaker exists per item or per run to bound autonomous spend; (7) the control plane supports at minimum pause/resume and a bounded single-step mode.
- **Keep:** all standard security checks, heightened — this type executes LLM-directed code with tool and network access inside sandboxes. No secrets in the sandbox image or any mounted volume; the declared tool/skill allowlist per stage is actually enforced at the sandbox boundary, not just documented; resource limits (CPU/memory/time) are set per sandbox; any downstream credential an agent acts through (target-system access, third-party APIs) is scoped and revocable independent of the harness's own secrets.
